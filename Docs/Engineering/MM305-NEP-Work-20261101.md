## Changes and limitations

- STS inner elevons and body flap are assigned pitch, outer elevons roll,
  rudder yaw, using installed OV-100 part names and read-back. Unknown parts
  retain their settings. This is not proof of physical axis response. The
  current code preserves flap deployment; it does not yet calculate or apply
  a measured body-flap deployment trim.
- The default Final alignment distance is now 2,286 m before the selected
  threshold; existing explicit JSON configurations retain their old value.
- A provisional NEP solver prices the existing modeled Final profile from
  that point to touchdown, searches a dynamic-pressure/configuration-bounded
  speed interval for configured landing speed, and returns no target if the
  modeled solution fails constraints. MM305 ranks priced candidate NEP speed
  against this target. This is point-mass model evidence only: the bisection
  assumes a monotonic modeled touchdown-speed response and has not been
  validated; failure to find a root is not proof no NEP exists. The result is
  recorded in the planning proposal. It is not yet a complete measured-state
  closed-loop NEP target, nor is CoM explicitly modeled as an aerodynamic
  moment shift.
- Once MM305 owns control, a fresh finite best-search geometry is retained
  even when its physical feasibility assessment is advisory. The existing
  inlet admission verdict and unpriced-tail information are preserved.
  Advisory telemetry no longer gives invented arrival times to zero-speed,
  unpriced geometry. Control of infeasible cases remains unvalidated.
- Removed synthetic lift/drag stress-case executions from the live terminal
  planning path. This does not establish robustness or qualify a landing.

## Subsequent static review — 2026-11-01, after the earlier debug build

This appendix supersedes the outdated status bullets above where they describe
Swift as lacking split-rudder discovery or automatic trim logic. This pass made
only surgical source/configuration edits. It did not run KSP, a replay, a
simulation, a unit/integration test, or a flight, and did not rebuild/replace
the running controller. A syntax-only `swiftc -frontend -parse` of the
changed Swift source files and `git diff --check` returned successfully.
This does **not** establish type checking, behavior, model fidelity or
flight qualification after these edits.

### Corrected source-level defects

- `ApproachGuidanceEngine.canCapture` now requires measured along-track
  position to lie within one guidance sample of the NEP station on **both**
  sides, instead of allowing capture arbitrarily far after the NEP. The
  modeled Final suffix must still be feasible.
- `TerminalRecoveryGuidanceEngine` no longer resets the NEP refresh timer
  every tick by reusing an older planning result. It re-solves the nominal
  Final-entry state from the latest measured shuttle state at the configured
  terminal cadence, retaining the provisional point-mass scope.
- `STSSurfaceActuators` now discovers each split-rudder half's
  `ignorePitch`, `ignoreRoll`, and `ignoreYaw` fields, writes yaw-only
  allocation to both halves and checks both after the kRPC
  `ControlSurface` settings. Arming fails when the two expected channels
  are missing. This addresses the second-module omission demonstrated by
  comparison with historical C `ee34f61`, but read-back of module flags
  cannot certify actual force/moment response, deployment sign or yaw/brake
  effectiveness.
- A failed kRPC control batch invalidates the deployment command cache, and
  the next accepted command reasserts a consistent full surface deployment
  request; no assumption is made that a failed batch was atomic.
- The NEP model retains a gear-down state already measured on the vessel,
  rather than projecting a clean-gear Final at higher reference altitude.
- `Configuration/sts.json` now explicitly sets
  `guidance.finalApproachDistance=2286` metres. It previously overrode
  the Swift default with 8000 m. Other explicit profile files, including
  historical/experiment configurations, were not changed, and a launch
  copying another profile can still override this NEP distance.
- A configured full-deployment speedbrake drag area must be finite and
  positive; neither that area nor a body-flap trim coefficient has been
  fabricated or enabled in `sts.json`.

### Still unresolved / must not be called flight-qualified

1. The NEP bisection assumes monotonic modeled touchdown-speed response.
   The provisional state projects the measured mass/configuration onto the
   Final geometry; it is not a demonstrated reachable closed-loop NEP state
   under the measured turn, pitch and CoM moments.
2. `LandingMissionController` still has a low-altitude
   `approach.update` recovery path without successful `canCapture`;
   `ApproachGuidanceEngine.update` can initialize a provisional capture.
   Its emergency control intent must be separated from a **qualified Final
   ownership transition** without losing the last-ditch recovery law.
3. Surface flags and requested deploy angles have read-back, but not a
   measured aerodynamic response matrix, sign-resolved split-fin angle,
   Mach/q dependent body-flap trim effectiveness, brake drag increment or
   rate limit. This cannot be inferred from kRPC field values alone.
4. A body-FRD CoM observation exists, but the trajectory and pitch
   model do not yet demonstrate correct center-of-pressure moment changes
   for payload mass/position. Payload topology changes also require care
   with cached part/module identifiers.
5. Existing MM305 flight logs demonstrate rapid energy loss but not a
   matched prediction made from the same measured state and command. Do
   not infer which physical effect caused it from the endpoint alone.
